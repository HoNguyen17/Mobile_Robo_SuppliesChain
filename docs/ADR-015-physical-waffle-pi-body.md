# ADR-015: Robot Body = Physical TurtleBot3 Waffle Pi at Scale 4

**Status:** Accepted 2026-10-04; acceptance run passed 2026-10-05 (reported by the user) · supersedes [ADR-013](_archive/2026-10-04-kinematic-cube-plan/ADR-013-kinematic-robot-body.md) · re-activates [ADR-010](ADR-010-robot-scale.md) (scale 4, physical part) and [ADR-011](ADR-011-physics-standard.md) · amends [ADR-009](ADR-009-simulation-clock.md), [ADR-012](ADR-012-custom-python-navigation.md) and [ADR-014](ADR-014-ros-interfaces.md)

**Acceptance run passed 2026-10-05 (reported by the user, no per-run figures).** This change was accepted when the robot, driven by ROS, makes 5 consecutive runs HomePoint -> point in front of the `TurtleBotNavigator` target shelf -> HomePoint, each with `leg_result = succeeded`, a stop within 0.15 m of the goal, no collision and no tip. The user reported that this was met, driven by ROS (`ros1/turtlebot_control`). It was part of the P1 exit ([milestones.md](milestones.md)). Out of scope for it: the `mission` node, the database, the S-xx scenarios, the scan-based obstacle layer, NPCs, recovery behaviours and per-category inflation profiles.

## Context
[ADR-013](_archive/2026-10-04-kinematic-cube-plan/ADR-013-kinematic-robot-body.md) replaced the physical Waffle Pi of `Nguyen-planning` with a kinematic `Cube`. Nguyen now wants the verified physical body and physics standard back, and keeps the A* planner and path follower of `Nhan-turtlebot` ([ADR-012](ADR-012-custom-python-navigation.md)). The Cube is dropped and its files are archived.

## Decision
1. **Body.** The URDF-Importer model `turtlebot3_waffle_pi`: `ArticulationBody` wheels driven by `DiffDriveController` (speed ramps 1 m/s² linear and 3 rad/s² angular, holding brake `WheelHold`), as built and verified on `Nguyen-planning` (commit `ff8fb31`). `CmdVelSubscriber` feeds it from `/cmd_vel`.
2. **Scale and units.** Scale **4** on the robot root: 1 robot metre = 4 Unity units, gravity 39.24 m/s² ([ADR-011](ADR-011-physics-standard.md)). ROS sees robot metres: positions, map origin, cell size and scan ranges are divided by 4 on the way out. `/cmd_vel` is read in robot metres and `DiffDriveController` applies the scale (its wheels are scaled 4x, so the same command gives 4x the Unity speed). ROS x = Unity Z / 4, ROS y = -Unity X / 4. All numbers in [test-plan.md](test-plan.md) are robot metres.
3. **Pose and TF.** `RobotPosePublisher` publishes the ground-truth pose of the moving body on `/robot/pose` (`PoseStamped`, frame `map`, 30 Hz, simulation time) and the TF `map -> base_footprint`. No AMCL. `/robot/pose` replaces `/cube/pose`. `/odom` stays, with its TF off (`publishTf = false`), so `base_footprint` has one parent. *Robotics > Warehouse > Add ROS Bridge* sets this up (idempotent). It has been run, and the scene `Warehouse.unity` is saved with `RobotPosePublisher`, `WarehouseMapPublisher` and `CollisionReporter`.
4. **Map from the static colliders.** `WarehouseMapPublisher` builds `/map` at every Play from the colliders of **static** `PhysicalBody` objects (walls, racks, stations) that reach into the band 0.03 to 1.0 m above the robot base. The grid is raw (not inflated), 0.05 m cells, 1 Hz, frame `map`. The scene has 14 static `PhysicalBody` objects (shell, stations, 12 racks); the 81 boxes are dynamic and not in the map. In the first Unity session the build gave 317 x 317 cells, origin (-7.70, -8.15) in `map`, 3.7 % blocked, from 120 colliders in 219 ms.
5. **Collisions.** Contact is a collision. `CollisionReporter` publishes `{other_tag, sim_time_s, x, y}` as JSON in a `std_msgs/String` on `/sim/collision`, with `other_tag` one of `Wall`, `Shelf`, `NPC`, `Obstacle`. Debounced to 1 s per object, where the object is the tagged object found from the hit collider up to its `PhysicalBody` owner, so a rack counts once, not once per leg or board, and reports `Shelf`. Floor contacts are ignored.
6. **Clock.** Unity publishes `/clock` ([ADR-009](ADR-009-simulation-clock.md)), nodes use `use_sim_time`. When Play restarts the clock, the running leg ends `aborted` / `cancelled` and the nodes carry on.
7. **Sensors kept, unused.** `/odom` and `/scan` stay as built on `Nguyen-planning`. Navigation does not read them. The scan-based obstacle layer of ADR-012 comes later.
8. **`TurtleBotNavigator`** (HomePoint -> target shelf -> dwell -> home) stays as a Unity-only test mode. `autoStart` is off in the scene; the Play Mode tests call `GoToTarget()`.
9. **Navigation package `turtlebot_control`.** `astar_planner` and `path_follower`, the algorithm of `cube_control`, no `move_base`. Defaults: `/nav/max_lin` 0.26 m/s, `/nav/inflation_radius` 0.35 m. Follower: 20 Hz, waypoint tolerance 0.15 m, final tolerance 0.10 m, maximum angular speed 1.0 rad/s, stops when `/robot/pose` is older than 0.5 s. Runbook: [turtlebot_control/README.md](../ros1/turtlebot_control/README.md).
10. **Footprint and inflation.** The Waffle Pi reaches **0.257 m** from the wheel axis centre (older documents: 0.21 m; ADR-013: about 0.22 m). With inflation 0.35 m the clearance is about 0.09 m.

## Consequences
- Wheel dynamics, `/odom`, the physics standard and their Edit Mode and Play Mode tests are back in the code base (green in the Unity Test Runner, reported by the user on 2026-10-05). Unity rebuilds the map at every Play, so a saved map never goes stale.
- Collisions are physical: static shelves and walls stop the robot, and `CollisionReporter` records them for the metrics. The robot can also tip or slide, which the Cube never did.
- Dynamic boxes lying in an aisle are **not** in the map (only static bodies are). The planner does not see them until the scan-based obstacle layer exists.
- **Open: clearance.** The S-01 threshold of 0.15 m cannot be met with inflation 0.35 m (and S-02, 0.10 m, is also just above 0.09 m). Not decided here: settle it at the first S-01 dry run, with a proximity cost in A* or the one allowed threshold revision ([test-plan.md](test-plan.md)).
- Only scale 4 is verified (at scale 1 the robot pivots weakly). Another scale needs the ADR-010 checks re-run.
- The "mast or arm upsets the balance" risk of the [manipulator feature](features/mobile-manipulator-inventory/requirements.md) is back; ADR-013 had removed it.
- Archived, not deleted: the Unity side of the Cube prototype in [`_archive/unity-cube-prototype/`](../_archive/unity-cube-prototype/README.md). After the acceptance run passed (2026-10-05), `ros1/cube_control` and `README_ROS1_Prototype.md` moved to [`_archive/ros1-cube-prototype/`](../_archive/ros1-cube-prototype/README.md) and ADR-013 to [`docs/_archive/2026-10-04-kinematic-cube-plan/`](_archive/2026-10-04-kinematic-cube-plan/README.md).
- **The robot does not spawn on the HomePoint.** The first Unity session (2026-10-05, read from Unity's `Editor.log`) logged, in robot metres in frame `map`: HomePoint x = 6.32, y = 5.87; target shelf x = -3.75, y = -3.13; robot at start x = 5.01, y = -0.05, which is about 6 m from the HomePoint. Not decided: a run either starts with a drive to the HomePoint, or the robot is placed on the HomePoint first.
- **Verified:** 109 Python unit tests (Windows with Python 3.14, and WSL with Python 3.8.10) with a closed-loop Waffle Pi model whose 0.257 m footprint never touches a wall; the real nodes against a fake Unity in WSL (scenarios A to I); the C# assemblies compile offline with Unity's Roslyn and 30 pure Edit Mode tests pass outside Unity (2 more need the Unity runtime and are skipped there). The Unity project (2021.1.11f1) opened and imported without a compile error, with the packages resolved (ROS-TCP-Connector at the pinned commit, URDF-Importer). Play was pressed once without the ROS endpoint, so the "Connection to 127.0.0.1:10000 failed" lines in that log are expected.
- **Reported by the user on 2026-10-05 (no figures):** the Edit Mode and Play Mode tests are green in the Unity Test Runner, and the acceptance run passed (the integrated Unity + ROS run).
- **Still open:** whether `/map` and `/robot/pose` look right in RViz (not reported), the S-01 and S-02 clearance (above), the category inflation values, the scan-based obstacle layer and the `mission` node.

## Alternatives rejected
| Option | Why not |
|--------|---------|
| Keep the kinematic Cube (ADR-013) | Collisions are only reported, the wheels do not turn, and the verified body and physics standard stay unused |
| Physical Waffle Pi with `move_base` | Adds AMCL, costmaps and tuning; the team code base is the custom planner ([ADR-012](ADR-012-custom-python-navigation.md)). The `move_base` plan stays on `Nguyen-planning` |
| Ground-truth map drawn by hand | Goes stale when the warehouse changes and has its own origin and scale. Unity builds the map at every Play |
| Map from the scan only | A scan map exists only where the robot has been, so a mapping run would come first. Mapping is not graded |
